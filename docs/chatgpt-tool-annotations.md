# ChatGPT tool annotations

Per-tool `readOnlyHint`, `openWorldHint`, and `destructiveHint` values for the hosted Magic Hour MCP server (`https://mcp.magichour.ai/`), with justification text written for OpenAI's app-review portal (the per-tool fields behind the `annotations_required` and `justification_required` errors). The justification cells below are the same strings as `chatgpt-app-submission.json` and can be pasted as-is.

Sources of truth, kept in agreement by tests:

- `mcp_magichour/openapi_policies.py`: `tool_annotations()`, `is_read_operation()`, and `DIAGNOSTIC_LOGGING_COUNTS_AS_WRITE`. OpenAPI-derived tools are classified from HTTP method and path in `customize_openapi_component()` (reviewed GET paths are read-only, DELETE is destructive, everything else is a write; unreviewed routes raise). Custom helpers pass explicit annotations in `mcp_magichour/openapi_server.py`.
- `chatgpt-app-submission.json`: `tools[*].annotations` and `tools[*].justifications`.
- `tests/test_openapi_server.py`: pins the 44-tool classification and asserts that the exposed tools, the submission JSON, and the table in this document agree.

Definitions applied (OpenAI app review, "Tool annotations"):

- `readOnlyHint`: true only if the tool strictly fetches, looks up, lists, or retrieves data and does not modify anything; false if it can create, update, or delete anything, trigger actions (send messages, run jobs, enqueue tasks, write logs, start workflows), or otherwise change state.
- `destructiveHint`: true if the tool can delete, overwrite, or irreversibly change data.
- `openWorldHint`: true if the tool accesses the public internet or open-ended external entities; false if it is limited to a bounded private account or workspace, even when externally hosted.

Summary, verified against `tools/list` from the built server: 44 tools; 12 read-only and 32 writes; 3 destructive (the project deletes); 0 open-world.

## Decision log

### readOnlyHint: diagnostic request logging is telemetry, not a tool action

PR #63 set `readOnlyHint=false` on every tool because OpenAI's definition lists "write logs" among the actions that make a tool non-read-only, and `ToolCallLoggingMiddleware` (`mcp_magichour/tool_logging.py`) logs every invocation. That reading is defensible but has a real cost: ChatGPT treats any tool with `readOnlyHint=false` as a write action that needs user confirmation before each call. The status and download helpers are called repeatedly inside one generation (`wait_for_*_project` polls until the project is terminal; `*_projects_retrieve_details` is the manual poll), so the all-false policy would prompt the user on every status poll, break the start-job / wait / show-result flow, and describe a lookup as though it changed something.

This branch draws the line at what the Magic Hour API call does. The middleware records only the tool name, redacted arguments (URLs, file paths, prompts, and secrets are replaced with `[redacted]`), and success or failure, to the server's own process log. It is not user-visible, is not stored in the user's account, cannot be requested or observed by the model, and is the same request logging any hosted HTTP service performs. It is therefore treated as infrastructure telemetry, and `readOnlyHint=true` is reserved for tools whose API call is a pure read: `ping`, `account_retrieve`, the three `*_projects_retrieve_details`, `face_detection_retrieve_details`, the three `fetch_*_download`, and the three `wait_for_*_project`. Everything that creates a project, starts a task, issues upload slots, or deletes stays `readOnlyHint=false`.

The disclosure is still made, without overstating it: read-only descriptions end with "Read-only; only server diagnostic logging of request metadata occurs." while write descriptions keep PR #63's "Calls write private diagnostic logs, including for status and download reads."

Reverting is a one-line change: set `DIAGNOSTIC_LOGGING_COUNTS_AS_WRITE = True` in `mcp_magichour/openapi_policies.py`. Every tool then reports `readOnlyHint=false` and carries the write-logging sentence, exactly as in PR #63 (`test_diagnostic_logging_flag_restores_all_write_hints` covers the flip). The classification pinned in `tests/test_openapi_server.py`, the submission JSON, and this table would then need to be regenerated, which is intentional: they record the decision in force.

### openWorldHint: false for every tool, including URL-accepting inputs

Every tool acts on the authenticated user's private Magic Hour account through Magic Hour's own API and storage; none browses the public internet, publishes content, or contacts external recipients, so all 44 tools are `openWorldHint=false`.

Some inputs can name public media. Every `*_file_path` field accepts "a direct URL to the file" as well as a Magic Hour `file_path`, and `animation_create_video`, `face_swap_create_video`, `lip_sync_create_video`, and `video_to_video_create_video` also accept `youtube_url`. The MCP tool never fetches those URLs: it forwards the string to Magic Hour's API, and Magic Hour's backend downloads the media into the account's private storage as part of the private job. The per-tool justifications for those tools say so explicitly. The only tools that download anything themselves are `fetch_*_download` and the inline-download option of `wait_for_*_project`, and `_fetch_media_bytes` rejects any host other than `https://videos.magichour.ai` before making a request. `ping` does not leave the MCP server at all.

### destructiveHint: only the project deletes

`video_projects_delete`, `image_projects_delete`, and `audio_projects_delete` permanently remove rendered media, so they are `destructiveHint=true` (and, as writes, `readOnlyHint=false`). Generation tools always create a new project and never overwrite the source media or an existing project. `video_assets_generate_presigned_url` signs URLs for new unique storage paths. `face_detection_detect_faces` creates a new task. All of those are `destructiveHint=false`.

### Tools that are not exposed

`upload_file_to_presigned_url` is not registered on the hosted server (`test_server_does_not_expose_local_filesystem_upload_tool` asserts this), so it has no row above and no entry in the submission JSON. If it is ever exposed it must be annotated `readOnlyHint=false` (it writes bytes to storage), `destructiveHint=false` (it PUTs to a fresh presigned path and never overwrites existing media), and `openWorldHint=false` (it only uploads to Magic Hour's presigned storage URL).

### Enforcement note

fastmcp 3.4.7 catches exceptions raised by `mcp_component_fn` and logs a warning, so the fail-closed `ValueError` for an unreviewed route does not remove the tool; it leaves the tool exposed with `annotations=None`. `test_every_exposed_tool_has_explicit_submission_hints` is the check that actually fails the build, which is how the new `GET /v1/account` route was caught.
